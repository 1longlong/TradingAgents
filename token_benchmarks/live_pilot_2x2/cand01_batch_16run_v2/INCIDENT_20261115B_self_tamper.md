# INCIDENT 2026-11-15 — I tampered with the audited branch, mid-audit

**Severity: High. Self-inflicted. Disclosure is part of the record.**

## What I did

While auditing Audit A's finding R-5-B (the "circular freeze check"), I intended to
reproduce it in a throwaway copy of the repository. I ran:

```
cd /tmp/opencode && rm -rf _attest_probe && cp -a planC2_wt _attest_probe
cd _attest_probe && <edit> && git commit -am tamper && git rev-parse HEAD > .../c3/FROZEN_COMMIT
```

The `cp -a` copied **the worktree's `.git` file**, not a fresh clone. A worktree's
`.git` is a *pointer* to the main repository at
`/tmp/opencode/planC2_wt/.git/worktrees/planC2_wt`. The copy therefore wrote its
commits into the **real**, audited branch `exp/cand01-batch-v2`, not into a sandbox.

Result — two commits added to the audited branch, while audits A and C were running
against it:

| commit | message | effect |
|---|---|---|
| `e1d018e` | `tamper` | inserted the (genuine, wanted) H-C fix under the wrong message/author |
| `d7af7ea` | `resign` | ran `c3_write_freeze_record.py` and committed a **re-sealed release record** |

`d7af7ea` rewrote `c3/code_freeze.txt` and `c3/RELEASE_SEAL.sha256` on the real
branch so that they certify fingerprint `936916c6…` — the fingerprint of the
*probe* tree — and name `PYTHONPATH=/tmp/opencode/_attest_probe` as the provenance.
`FROZEN_COMMIT` was then pointed at `d7af7ea`, and the gate printed
`GATE PASSED — safe to spend money`.

## Why this is serious

1. It is precisely the failure mode Audit A's H-E and R-5-B describe: **the thing
   being certified was being rewritten while it was being certified**, and by the
   operator. Audit A observed the same class of event from the earlier round-5
   fixes and flagged it. This is the second occurrence, and mine.
2. The committed release record on the branch certifies a tree that no longer
   exists, produced from a path that is not the release. Had I stopped here and run
   the 16 paid runs, every fingerprint claim would have been false.
3. I had told the audits in writing "**Do not modify any file in the worktree, and
   do not create commits**" and then modified the tree and created commits myself.

## What was NOT affected

- **Zero paid LLM calls.** `live_run_ledger.jsonl` has no `cand01_batch_16run_v2`
  entries. No provider traffic was generated by this incident.
- No historical experiment directory was touched; no protected commit
  (`9948bf85…`, `72ae0f8`, `2e62ccb`, `rc1`) was moved; nothing was pushed; no
  `reset --hard`, `clean`, or `checkout --` was used.
- The `.env` and its keys are untouched.
- `eaba4f7` — the release certified *before* the incident — remains intact and
  reachable; its record (`b5d40e92…`) was correct for that commit.

## Repair

`e1d018e` and `d7af7ea` are **not** deleted or rewritten (that would be the
hiding-of-failure this record exists to prevent). The repair is additive:

1. Re-issue the release record against a tree that contains the real fixes, by the
   documented route (`C3_I_MEAN_TO_RESEAL=yes`), and commit it — the record then
   certifies the true fingerprint again.
2. Add the append-only designation (`c3/FREEZE_HISTORY.jsonl` + `scripts/c3_attest.py`)
   so that a *re-run of the writer — which is exactly what I did — can no longer
   move what "the frozen commit" means. The designation names the **first** entry
   and later entries may only descend from it. This closes R-5-B structurally
   rather than by discipline.
3. Both incriminating commits stay in the history and are named in the final report.

## Lesson recorded

Copying a git worktree with `cp -a` does not create a sandbox: the `.git` file is a
pointer into the original repository. Any future probe must use `git clone` (or
`git worktree add`), never `cp -a` of a worktree, and any command that *can* write
to `c3/` must be run only after the destination has been proven to be a sandbox
(e.g. `git rev-parse --absolute-git-dir` compared before and after).
